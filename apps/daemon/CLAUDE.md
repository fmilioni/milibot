# Daemon (milibotd)

## Tests

- Layout mirrors `src/`: `test/<same path>/<module>.test.ts` (runtime domains in `test/runtime/<domain>/`), `test/support/` for fakes and harnesses, `test/fixtures/`. `process-boundaries.test.ts` and `windows-hide.test.ts` scan the sources.
- Fakes: agent fakes from `@milibot/agent/testing` (production code takes `FakeProvider` from `@milibot/agent/llm`, never `./testing`); `FakeVmCli`/`fakeGuest()` in `test/support/` (the fake guest's `/procs` and `/exec` run real local processes, `/workspace` swapped for a temp dir).
- Integration tests boot through `bootRuntime` (`runtime-harness.ts`, `stopRuntimes()` in `afterEach`) or `startSupervisor` (`supervisor-harness.ts`); temp dirs and polling via `temp.ts`/`wait.ts`. Tests seed the workspace in `'en'` unless they are about Portuguese.
- `runtime/browser/page-script.int.test.ts` and `runtime/design/render.int.test.ts` use a **local** headless Chrome (`test/support/local-chrome.ts` or `MILIBOT_TEST_CHROME`; skipped without one). Other design tests inject a fake `DesignRenderBackend` and font fetcher; skill import tests point `githubApi` at a local server. Never the real network.

## Process layout

- `supervisor/` and `runtime/` never import each other; what both need sits in top-level modules (`ipc/`, `host/`, `golden/`, `db/`, `backup/`, `util/`, `handlers.ts`, `vm-cli.ts`…). `process-boundaries.test.ts` checks that `main.ts` loads no other runtime code.
- A workspace database is reached only through `workspace-db/`, which may take only the runtime's store modules. The supervisor reads a DB a runtime may hold only in `readonly-queries.ts`, with tables and columns of the baseline migration (a test runs them against a DB migrated to it alone); the runtime never reads `app.db` (the "on close" setting arrives as `MILIBOT_CLOSE_BEHAVIOR` and a `close_behavior` IPC message).
- **Configuration** (`config/env.ts`): every `MILIBOT_*` variable is parsed once, with zod, into `DaemonConfig` or `RuntimeConfig` (plus `RUNTIME_ENV`, what the supervisor forks a runtime with); modules take typed values, never `process.env`. A new variable goes in the schema and in the root CLAUDE.md table (`test/config/env.test.ts` compares them).
- **Errors**: `toApiError` (`errors.ts`) is the one mapping of a thrown error to `{code, message, details}`, for HTTP and the runtime's IPC answers. Services log through a `LogFn`.
- **Supervisor** (`src/main.ts`, `supervisor/`): listens on `127.0.0.1`, writes `<dataRoot>/daemon.json` (0600, with the bearer token everything requires; WS: `?token=`), never deleted on shutdown: the next daemon reuses port and token.
- `WorkspaceSummary.vmState` (the switcher's status of every workspace) is the running runtime's last `vm.status`, republished as `workspace.updated` on each change; without a runtime, `probeVmState` (`supervisor/overview.ts`) reads it from the workspace's files.
- **Runtime per workspace** (`runtime-main.ts` → `createRuntimeFromConfig` in `runtime/process.ts`, seams replaceable through `RuntimeProcessOverrides`): forked on demand, owns its `workspace.db` exclusively; if it dies it becomes `crashed` and restarts on the next request. Runtime → supervisor calls: `ipc/calls.ts` (`RuntimeCallMap`).
- **Background** (`supervisor/autostart.ts`): a new daemon starts the runtimes of workspaces with `last_running` and (enabled routines or `keep_running`) with `MILIBOT_RUNTIME_BACKGROUND=1` (a `suspend_vm` workspace doesn't boot the VM until `open`). The workspace's `vmAutostart` preference and `MILIBOT_VM_AUTOSTART=0` keep the VM off on start and `open` (`vmAutostart()` in `runtime/process.ts`); a QEMU left running is still adopted.
- **Migrations** (`db/migrations/{app,workspace}/NNNN_<name>.ts`, each a default-exported `Migration` imported explicitly by that folder's `index.ts`; `db/migrate.ts` applies versions contiguous from 1, one transaction each, tracked in `PRAGMA user_version`, and refuses a database newer than the code):
  - Every schema change is a new migration with the next number, then `pnpm db:snapshot` regenerates `schema.sql` (a test compares it). A migration on `main` is never edited, `0001_init` included.
  - **At most one new migration per PR per database**: while the branch is open keep editing that one, and fix your own dev/test DB by hand after changing it (undo it and set `PRAGMA user_version = <n-1>`, or delete your own scratch data dir, never another agent's); from sources, `openMigrated` refuses a DB whose tables differ from what its version creates. After rebasing onto a `main` that gained a migration, renumber yours. `pnpm check:migrations [baseRef]` enforces this; it loads each file standalone, so migrations use only `import type`.
  - A migration that rebuilds a table with FKs uses `foreignKeysOff` (the runner turns `foreign_keys` off outside the transaction and requires an empty `foreign_key_check`).
- **Secret store** (`secrets/`, chosen once by `resolveSecretStore` in the supervisor and exported as `MILIBOT_SECRET_STORE` so every runtime uses the same):
  - macOS: Keychain via `security -i` stdin, which reads 4096-byte lines and runs the overflow as new commands. Linux/Windows: `@napi-rs/keyring`, Linux pinned to the Secret Service (the keyutils fallback loses everything on reboot). `IndexedEntrySecretStore` splits values longer than an entry holds into chunks (MCP OAuth records exceed both limits).
  - Without a keyring: the AES-GCM `EncryptedFileSecretStore`, reported by `GET /host` so the app warns (never silent); file secrets move into the keyring once it answers. After the keyring has worked once, the `secrets/keyring-in-use` marker keeps it (`keyring_unreachable` instead of falling back).
- **Workspace setup** (`supervisor/workspace-handlers.ts`, `golden/`, `runtime/setup/`): `setup_step` `providers → vm → login → done` (only `done` shows the chat; created through the API without `setup: true` it starts `done`). A missing or outdated golden triggers the detached build (`GoldenBuilder`, survives the daemon).
- **Host probes** (`host/`, reported through `GET /host`): `windows-hypervisor.ts` → `vmAccel` (`whpx_feature_disabled`, `whpx_reboot_pending`, `virtualization_disabled` are names the desktop keys on and mean TCG, also for the golden build; `unknown` still tries WHPX); `info.ts` → `qemu` (the bundled QEMU, `bundledQemu` in `profile.ts`; a PATH QEMU only without it); `setup.ts` → `setup` (Linux KVM status), computed from the daemon's own process, which QEMU inherits: a daemon started before the user joined `kvm` reports `relogin` until it restarts. Probes are injected; never test against the real system.
- **Bots**: `linux_uid` and slug are never reused (slug starts with a letter, becomes `bot-<slug>`); `display_num` = lowest free. Delete = soft delete + removal of the user/desktop in the VM (deferred to the next boot while stopped; then `display_num` becomes `-rowid`).

## Agent runtime

- **Composition** (`runtime/composition/`): `createContainer` (`container.ts`) is the only place services are built, in dependency order.
  - A service used before it exists is a `lazy()` reference, read only at run time (`get` throws before `set`); bots hand their deletion to other services through `BotService.onDeleting`/`onDeleted`.
  - `collectHandlers`' result is typed as every `/w/` endpoint, so a missing route fails typecheck. `ToolRegistry` refuses to build unless each catalog tool (`TOOL_NAMES`) has exactly one owner (the agent host owns `HOST_TOOL_NAMES`).
  - A `Component` of the `Lifecycle` starts in the order added and stops in reverse (the VM is added first, so it stops last). `agent-env.ts` adapts the services to the agent's ports; messages go through one `MessageWriter` (`runtime/messages/writer.ts`: redaction, events, streamed-delta safety).
- **Domains** (`runtime/<domain>/`): `index.ts` is the public surface; `service.ts`; `store.ts` holds ALL the SQL of the domain's tables and never touches another domain's tables; `tools.ts`/`tools/`; `handlers.ts` or `service.handlers()`; `scripts/`. Constructors take one `deps: <Domain>Deps`. `process-boundaries.test.ts` fails on an import of another domain's internal file (only `store.ts` → `store.ts` is allowed). `runtime.ts`, `process.ts`, `workspace-store.ts`, `blobs.ts` belong to no domain.
- **Stores** by aggregate: `WorkspaceStore` holds only the bots, conversations, messages and settings stores over one database plus `deleteBot`, the transaction spanning bots and conversations. Cross-domain facts go through ports the container wires (`LinkTargets` for board links, `WorkSessionService.mergePrFolders()` for git policy, `BlobReferences`, where every domain that shows blobs registers its shas for debug retention).
- **Tools** (`runtime/tools-core/`): a family is `XxxTools extends ToolSwitch` (handlers run by `runToolSwitch`); arguments are read with `@milibot/agent/tools` helpers (strict ones throw an input error, lenient ones fall back); a family's own errors are mapped in `mapError`. Name references go through `resolveByRef` (id → exact folded name → substring), names compare with `foldKey`.
- **VM-side scripts** (`<domain>/scripts/*.{sh,js}`): real files, linted (`.js` as Node CommonJS; `browser/scripts/` as ES5 in pages; `design/scripts/` as browser) and shellchecked (`#!/bin/bash`); `pnpm gen:scripts` writes the committed `<name>.generated.ts` (`<NAME>_SCRIPT`; a test fails when stale). Values go through env vars, args or stdin, never interpolation. `design/scripts/inspect.js` stays a function declaration (evaluated as `(<script>)(width, height)`); `browser/scripts/page.js` hashes its own text, so any edit reinstalls the helper in open pages.
- **VM helpers** (`runtime/vm/`): `whenVmRunning`/`onVmTransition` for "when the VM comes up" (they also fire at once when it already runs; never subscribe to `vm` and test `state === 'running'`); `VmCopyQueue` for lazy copies into the VM (one run at a time, a kick during a run schedules one more).
- **CLI engine hosts** (`runtime/providers/cli-engines/`): a `CliEngineHost` per engine in `CLI_ENGINE_HOSTS` holds what the daemon does differently per engine (models, efforts, sign-in env, login terminal/status, plan source, image model, connection test, `createRuntime` with `prepare` and an optional `installer`). `CliEngineRoutes` (`cli-routes.ts`) serves `/cli/:engine/*` for all engines and throws `unsupported` (`{engine, capability}`) for a missing capability.
- **VM** (`runtime/vm/controller.ts`, over the host CLI and `@milibot/vm-host`): the running VM's `-smp`/`-m` come from `config.json` `running`, never from `ps`. `vm.guest()` boots if needed; `vm.runningGuest()` never boots. `close_behavior`: `suspend_vm` stops the VM when the last window closes; `keep_running` leaves QEMU running for the next runtime to adopt. `PORT_IN_USE` on start → the supervisor moves the VM to the next free port block (`MAX_PORT_MOVES`). A WHPX guest that hangs or logs failed interrupt injections → `waitForWhpxGuest` restarts it with `--whpx-kernel-irqchip off`.
- **Guest networking pitfalls** (don't remove): QEMU user-net hostfwd (before gvproxy) had backlog 1, so concurrent connections got `ECONNRESET` on macOS. Hence `GuestClient` retries with backoff, `runtime/vm/guest-transport.ts` uses two undici `Pool`s (`quick`, `long` for exec/streams) and opens connections one at a time, and neutralizes undici's `socket.setTypeOfService(0)` (uncaught `EINVAL` on a reset socket); `installProcessGuard` only logs uncaught transient network errors. Keep guest requests sequential whenever possible.
- **Milibot MCP** (`runtime/mcp-server/`): streamable HTTP on a random loopback port, reached from the VM at `10.0.2.2` (`GUEST_NET.host`, which gvproxy maps to the host's loopback); token per lane and CLI engine; exposes Milibot's tools minus the engine's native ones (the driver's `nativeInMcp`); everything goes through `host.runTool`.
- `apply_patch` (`runtime/code/tools.ts`) tries `-p1` → `-p0` → `--recount`, never `--recount` first. Hunks without line ranges (a bare `@@`, Codex's `*** Begin Patch`) get real ranges in `code/patch-hunks.ts` before `git apply` (each must match once after the previous one). Paths are never retried from another folder: a missing one is reported with the cwd used.
- `bash` runs with `NO_COLOR=1`/`FORCE_COLOR=0` (not `CI`, which changes tools' behavior) and its output is ANSI-stripped before it reaches the model.

## Domains

- **Browser** (`runtime/browser/`): text tools over the **same Chrome** as the bot's desktop, through CDP via a `RELAY_SCRIPT` relay as `agent` (`runtime/cdp/`, shared with design rendering). Connections drop on VM down, idle and any `CdpError`. Snapshots are the viewport's accessibility tree with `e<N>` refs never repeated within a bot, never raw HTML. Don't switch to the Playwright MCP (whole-page snapshots, heavy definitions).
- **Web** (`runtime/web/`): `web_fetch` downloads in the VM as the bot (`FETCH_SCRIPT`) and converts in the daemon. `BLOCKED_SUBNETS` (`url-policy.ts`) is the one list of refused addresses, checked by `normalizeWebUrl` and again by the script on every hop (the `lookup` hook for names, before connecting for IP literals, which Node never passes to `lookup`): hardening against pages steering bots at local services, not a sandbox. Parts stay at `PAGE_TOKENS` so a result never hits the host's cut. `web_search` calls Brave or Tavily from the daemon (key never sent to the VM); keyless scraping was dropped on purpose (CAPTCHAs, poisoned results).
- **External MCP** (`runtime/mcp/`; the agent keeps only config types, names and per-bot tool sets): `stdio_vm` servers run in the VM as `agent`; `http` is streamable with SSE fallback. CLI engines get them in the driver's `externalMcp` shape. OAuth (DCR + PKCE, loopback redirect in the runtime): for CLI engines the OAuth server is proxied by Milibot's MCP (`/mcp/x/<slug>`), so tokens never reach the VM.
- **Knowledge** (`runtime/knowledge/`, `runtime/embeddings/`): the `EmbeddingService` indexes corpora without knowing their domain (`embeddings/` imports none of them): document chunks are the `ChunkCorpus`; summaries, plans and boards are `VectorCorpus`es tracked by text sha (`sqlVectorCorpus`). Chunks never cross a page.
- Hybrid search uses weighted RRF (`lexicalQueryWeight`; equal weights make it worse). The local embedding model runs in a **child process** of the supervisor shared by all workspaces (only process exit returns onnxruntime's memory; EmbeddingGemma in q4, since q8 dequantizes on every run). Per-model thresholds in `runtime/embeddings/thresholds.ts`, measured with `eval:knowledge-thresholds`.
- **Repos**: `repos/scripts/checkout.sh` (also the session worktree) fetches, fast-forwards the shared clone and a clean reused worktree, and reports `BEHIND` when the bot's branch has commits of its own; bots that aren't Claude Code depend on it to never work on stale code.
- **Repository instructions** (`repos/instructions.ts`, `scripts/instructions.js`): one `node -e` exec as the bot per call (never the shared `agent`, so unreadable files stay out); the repository root is the closest `.git` (a file in worktrees) and the walk never leaves `/workspace`. `[]` while the VM is down (`runningGuest`, never boots it). `LlmCallStore` stores a call's `instructionFiles` inside `request_json` (insert and update), which the debug view reads with `json_extract`.
- **Work sessions** (`runtime/sessions/`): conversation `type 'session'` + its own lane; `subagent` helpers (depth 1).
  - Folder (`cwd`, fixed at `open()`): the repo worktree, else the `folder` given (`session_start` or `plans.folder`), else `/workspace/sessions/<slug>-<id8>`. A given folder goes through `sessionFolder` (`files/session-folder.ts`) and must not overlap another open session's; `files/scripts/folder.sh` makes it and reports its real path (a symlink out of /workspace falls back to `/workspace`).
  - Diffs (`sessions/diff.ts`, always with `DIFF_SCRIPT_ENV`; bash 3.2 compatible, since integration tests use the local bash): baseline = `HEAD` or a shadow repo under `/workspace/.milibot/sessions/`, the mode fixed at baseline. The shadow size limit counts only files `.gitignore` keeps; `DEFAULT_IGNORED` goes in a temp `core.excludesFile`, never written anywhere; a temporary index (`GIT_INDEX_FILE`), never the real one. Paths are `--relative` to the session folder, so blob lookups use `$BASE:./<path>`.
  - A finished session's patches are saved in `work_session_patches` (`patches_at`) when refreshed with the VM running; from then on `changes`/`fileDiff` read the saved ones. A reopened session measures live again.
- **Step lists** (`runtime/todos/`, one `TodoStore` for plans and sessions; sessions reach plans only through `SessionPlans`): `todo_write` merges (id, else title) and keeps steps left out, since weak models send partial lists; only a list naming every step reorders.
- **Models per piece of work** (`runtime/providers/model-request.ts`): what the bot names on `session_start`/`plan_write`/`subagent` is resolved against `ModelCatalog.catalog` (an exact id wins; ties return the candidates to the bot) into the `model_spec` `ModelChoice`. `set_model` (a bot's own model, or another's when it manages the team) goes through `resolveBotModelChange` instead, with the bot settings panel's rules: an effort the model does not list is refused, not narrowed, and the patch is applied through `BotService.update` (so `bot.updated` reaches the app). A bot with any open CLI engine lane gets its secret files owned by `agent` (one owner per bot: its API lanes then cannot read them).
- **Side-work models** (`runtime/providers/model-policy.ts`, the only place with the rule): the workspace choice, else the light model of the bot's provider (ignored unless an enabled chat model), else the bot's own model untuned. The Haiku preselection for Anthropic/OpenRouter lives in the form (`suggestedLightModel`).
- **Providers**: three objects built in order: `ProviderStore` (rows, secret), `ProviderClients` (API clients and the fake; `faked` makes `cliEngine` null so fakes never take the CLI path), `ModelCatalog` (resolution, CLI engine, light model).
- **Codex** (`runtime/providers/cli-engines/codex.ts`): `CodexInstaller` installs `CODEX_VERSION` when the VM comes up with a Codex provider, and every Codex process waits for it (`prepare`). Running app-servers reload credentials on a 401. The plan comes from the rate limits, never a CLI call. The `codex-image` model is offered only with a subscription sign-in.
- **Antigravity** (`runtime/providers/cli-engines/antigravity.ts`): `AntigravityInstaller` (a `VmCliInstaller`, like Codex's) installs the pinned agy build and its MCP bridge (`scripts/agy-mcp-bridge.js`, its sha is part of the installed version, so a changed bridge reinstalls). Sign-in status and quota come from `agy -p /usage`, which waits for a login when there is none (hence the timeout); the token file is never read. `host.quota` makes `CliPlanTracker.refreshQuota` read it after turns and usage views (`QUOTA_REFRESH_MS`); Gemini's windows are stored as `five_hour`/`seven_day`. `antigravity-image` pictures are read from agent's home by `readAntigravityImages` (names and conversation id validated before they reach the shell).
- Each engine's `createCliBackend` stops the labelled processes a previous runtime left in the VM once, before its own first process (a failed sweep is retried only until then, or it would kill this runtime's).
- **Skills** (`runtime/skills/`): the folder (`SKILL.md`, frontmatter `name` = folder name) is the content, the `skills` row the state; no `bot_skill_prefs` row = the skill's default. A folder copied into `<wsDir>/skills/` gets a `user` row on the next scan (`SkillLibrary` rescans on every catalog build, cached by file stats; `fs.watch` only hints). Bots only save/delete their own; every delete goes through `SkillService.remove`.
- **Skill import** (`runtime/skills/import/`): downloads go in `<wsDir>/skills/.imports/` (dot folders are invisible to the library and the watcher); `install` writes folder + row with no `await` in between (else the watcher's rescan creates a `user` row first). Zip entries with `..`/absolute/backslash/drive-letter names and symlinks are dropped. A GitHub ref with slashes is found by moving path segments into it on 404. Same origin → replaced in place (id and switches kept).
- **Skill files in the VM** (`runtime/skills/vm-sync.ts`): skills with extra files are mirrored root-owned to `/usr/local/share/milibot/skills/<slug>/`; a `.milibot-hash` per folder sends only changed skills (stay under the guest's `/exec` body limit). Backup restore is guarded by `skillEntryTarget`.
- **Designs** (`runtime/design/`; family `design` gated by the `design` skill):
  - `design/tools/` only parses and words results; operations live in `DesignFrames`, `LayoutChecks` and `DesignOutput` (built by `DesignService`). A `design_write_frame` draft is cleared through its `DraftCall` (after the save, or in the tool's `finally`).
  - Frames are HTML + Tailwind v4 compiled in the daemon (`compile.ts`) into a self-contained document (CSP without scripts or requests), cached by input hash.
  - Rendering for bots (`render.ts`): a headless Chrome in the VM; inspection through `Runtime.evaluate` (the page's CSP doesn't apply); PDFs use `shared/src/designs/print.ts` (same document as the desktop export).
  - Overlap math is in `shared/src/designs/placement.ts` so the app previews the same push.
  - Drafts (`design/draft.ts`): `DesignDrafts` compiles the streamed input of `DRAFT_TOOLS` uncached (`compileDraft`, never the LRU). Models may send `width` after `html`, so until then the draft borrows a size (`PHONE_NAME`); without a tool-call id a new call is told apart by its input not extending the previous one.
  - A fixed-height screen frame whose content runs past its bottom becomes `auto` after a write, moves clear of what it would cover and amends the saved revision (`amendFrameRevision`); paged sizes (`isPagedSize`) keep their height and report the overflow.
  - **Art frames** (`design_draw`; `art_status` NULL = an HTML frame): `ArtworkGenerator` (`design/artwork.ts`) is never stopped by the turn ending, only by deleting the frame, design or bot and by `close()` (rows left `drawing` fail at startup). `sanitizeSvg` writes its own XML (parse5's serializer isn't well-formed and an `<img>` refuses it). `data-art` references resolve at compile time (`artFor`, part of the cache key). Outcomes reach the bot on its next `design_*` result (`takeNotices`).
  - Archived designs leave `design_list` and name matching and refuse writes.
  - `.mbdesign` (`design/bundle.ts`): import always makes a new design and re-validates everything as untrusted (`checkThemes`/`applyTokenChanges`, `DESIGN_LIMITS`, a `maxBytes` cap on every entry, each asset's sha256 must match its name); a newer `formatVersion` is refused. The daemon writes the file itself at the path the app chose (`.partial` then rename).
- **Boards** (`runtime/boards/`): archived boards leave `board_list`/`board_search` and refuse bot writes. Card images are `asset:<sha>` blobs copied into the VM by a `VmCopyQueue` and shown to bots as their `/workspace/boards/` path. A bot moving a card to doing or opening a session on it joins the assignees, never replaces anyone. Links resolve through `LinkTargets` (boards never query plans, sessions or designs); moving to done is always the bot's (or the user's) call.
- **Pull request statuses** (`runtime/tasks/pr-status.ts`): task cards and board `pr` links not merged yet are read from GitHub every minute in one GraphQL query, from the daemon with the workspace token (without one, `gh api graphql` as the first bot in the VM); a failed poll changes nothing, and merged is final (never asked again). PRs match by `pullRequestKey` (canonical lowercased URL), so links typed with `/files` or another case follow too. A `gh pr` command's new status reaches every board link of that PR through `linkPullRequest`, not only the cards of the session it ran in.
- **LLM calls** (`runtime/observability/llm-calls.ts`): every write (`recordLlmCall`, `updateLlmCall` in the container) emits `llm_call.recorded` (the app's debug panel reloads on it) and updates the footer's spend; spend limits are checked only once a call is no longer `LLM_CALL_RUNNING`. `update` moves `created_at` to the write (calls are stamped when they end). Rows a stopped daemon left running become `interrupted` at startup (`closeRunning`).
- **Image generation** (`runtime/images/service.ts`): the protocol comes from the provider's preset or URL (`imageProtocol`). `generate_image` refuses options the model can't do (`checkImageRequest`) before any call, writes files as the bot (never overwriting; parallel saves reserve names in memory) and records one `llm_calls` row per prompt.
- **Routines** (`runtime/routines/`, pure `shared/src/routines/`): cron in local time (DST in `nextRunAfter`). The `routine_run` card is what the bot reads. Never stacks; later than `MISSED_AFTER_MS` = missed.
- **VM usage** (`runtime/vm/stats.ts`): the guest reads per-bot cgroup files of `milibot-bot-<slug>.slice` + `user-<uid>.slice` (only work run with `bot: <slug>` lands there). History in memory only, no WS event (the app polls while a usage view is on screen).
- **Settings**: invalid preference values fall back to the default; spend limits pause with `host.hold`; the GitHub token and secret values go only on `/exec` stdin; `GitPolicySync` writes `/etc/milibot/git-policy` (read by the `gh` wrapper) on VM ready and when PR preferences, plans or sessions change; VM operations that need the VM stopped run as a `task` (`runtime/vm/admin.ts`); backups are written to `.partial` and renamed at the end.
- **Attachments and chat files** (`runtime/attachments/`): chat files live only in the VM (`/workspace/uploads/…`, `queued` while the VM is off; the turn waits for the copy); `exportAttachment` streams one to the host on demand. Images a bot's final reply mentions are snapshotted into attachment rows and never reach the model context. `share_file` copies the bot's file into the uploads tree; its message's `payload.text` is the caption and `content` adds the VM path for models. A file gone from the VM becomes `removed` (`FILE_REMOVED`) instead of failing forever.
- **Set-aside requests** (`runtime/set-aside/`): the `set_aside_requests` rows behind the agent host's `env.setAside` (`SetAsideService.port()`) and the app's list/drop routes; every add, wake or drop emits `set_aside.changed` (the bot panel refetches). The host decides when to wake and when to alert; the daemon only stores. `workState` (sessions not ended, plans awaiting approval/approved/executing) is wired in `agent-env.ts`.
- **User requests** (`runtime/user-requests/`): `ask_user`/`request_secret` wait with `ctx.detach` (frees the slot); a late answer becomes a `user_answer` turn. Secrets by reference only (`{{secret:NAME}}` replaced in the daemon before typing; files in `/run/milibot/secrets/<slug>/` tmpfs). Output of Claude Code's native Bash doesn't pass through the daemon, so it isn't redacted.
