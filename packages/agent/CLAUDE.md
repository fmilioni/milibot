# Agent package

## Layout and public API

- `src/`: `host/` (the `AgentHost`), `environment.ts` (the ports the daemon implements), `cli/` + one folder per CLI engine, `llm/` (message model, `LLMProvider`, usage/pricing, providers; `llm/http/` shared by the chat, embedding and image clients), `tools/`, `prompts/`, `memory/`, `work-sessions/`, `groups/`, `mcp/` (config types, tool names, per-bot tool sets; the SDK client is the daemon's), `skills/` (SKILL.md format; the built-ins are the package's `skills/` folder), `embeddings/`, `images/`, `test-support/`.
- Consumers import only the entry points in `package.json` `exports`, each an explicit list: `.`, `./tools`, `./llm`, `./prompts`, `./cli`, `./embeddings`, `./images`, `./testing`. Production code never imports `./testing`; `FakeProvider` is also in `./llm` for `MILIBOT_FAKE_LLM`. Inside the package import the file itself, never an entry file.

## AgentHost (`src/host/`)

- **Layout**: `agent-host.ts` is the facade (`DefaultAgentHost`) and wires the `HostContext` (`context.ts`) every collaborator receives. Collaborators reach each other only through the context and only inside their methods (they import each other as types; only `agent-host.ts` and `turn/engines.ts` construct them), so wiring order doesn't matter. `turn/engines.ts` hands a turn to `native-loop.ts` or `cli-turn.ts`.
- **Turn input** (`turn/turn-input.ts`) is the one place that decides what a turn reads besides the conversation, in the same order for every engine: the turn's documents, then Milibot's notes, then what arrived. CLI chat turns put the project note first; native chat turns get the project in the cached system part.
- **Environment ports** (`environment.ts`): `AgentEnvironment` composes required ports, kept flat (`env.appendMessage`, not `env.chat.appendMessage`) so tests can replace one member and the daemon's adapter spreads one object per port; code that needs little takes a `Pick`. Nothing is optional: tests use `createTestEnv` (`test-support/env.ts`: no-op defaults, every tool family on, `'en'`, and an `InMemoryWorkSessions`, so session lanes always run the session path). Host state that must survive restarts goes through `hostState` (`settingsHostState` maps it onto `HOST_STATE_KEYS`/`cliKeys`: stored key strings, never rename). The env has no `setSetting`.
- Messages from the same conversation are coalesced in the queue. `pause` is persisted; after `release` (takeover) the next GUI action requires a screenshot; `stop` aborts and clears the queue, and late MCP tool calls are refused until the next turn.
- **Lanes** (`host/lanes.ts`): each bot has the main lane (key = `botId`), the internal lane (`<botId>:internal`: requests from other bots, so they never queue the user) and one per work session (`<botId>:<sessionId>`, sub-agents `…:sub:<n>`), each with its own queue, turn and CLI process. Chat-lane helpers (`<botId>:chat:sub:<n>`) are always read-only (`READ_ONLY_HELPER_TOOLS`, no external MCP, `CLAUDE_CODE_READ_ONLY_TOOLS`). `LANE_TOOLS`/`toolAllowedInLane` define the tools per lane kind (checked again by the tool gate).
- `computer`/`browser_*` lock the shared screen for the lane until its turn ends (others wait up to `screenWaitSeconds`). Session lanes compact at `sessionBudget`, and their CLI sessions rotate only for another model or profile.
- **Messages mid-turn** (`joinRunningTurn`): a user message in the conversation a turn is working on joins that turn (`turn.incoming`, `USER_WROTE_MEANWHILE_NOTE`) instead of queueing: the native loop reads it at the next step boundary or right before ending; CLI engines get it at once (`turn.deliver`). Claude Code may answer it after its `result` with a second `result`, so `runTurn` keeps reading until every sent message came back as a `--replay-user-messages` echo (`isReplay`). A turn that ends without reading it re-queues it. User messages go ahead of bot/routine/session requests.
- **What a turn reads**: `ReadTracker` (`host/read-tracking.ts`) keeps, per bot × conversation, the newest message the last turn's input saw; the next turn reads what came after it, and a `user_message`/`group_message` turn with nothing unread is skipped. Work reaching an ended session (late `bot_reply`, requests queued in its lane, `closeLane`) is redirected to the session's origin conversation (`redirectEnded`); a second `session_finish` is a no-op.
- **Bot↔bot flow** (`host/collaboration/bot-messaging.ts`): a reply wakes the sender (`BotMessaging.finish` → `bot_reply` turn), so a pair can bounce forever; three things stop it. `message_bot` with `expects_reply: false` enqueues nothing back. From `PAUSE_BOT_EXCHANGE_AT` round trips since the last user message, a new message is held in memory (`heldMessages`, lost on restart: the card expires) behind a `continue_bot_exchange` confirmation card (`host.resumeBotMessage` sends it with hops reset). `MAX_HOPS` stays as the silent backstop.
- The step limit never ends a turn without text: past it the model gets one call with `toolChoice: 'none'` (`STEP_LIMIT_NOTE`).
- `message_bot`/`ask_bot` also post a `bot_message_received` card (system author, invisible to models) in the target's DM; from a lane carrying an approved plan (`env.activePlan`) the request brings the plan id and steps so the target marks them with `plan_step`.
- **Other work and `after_current_work`**: models never see that card, so main and internal turns get `otherWorkNote` while another non-helper lane of the bot has work. `after_current_work` (main lane only) snapshots those lanes (`host/collaboration/other-work.ts`, in memory, one per conversation) and enqueues the task once each has gone free at least once (`laneFreed`); a session lane counts as free when its turn ends. A `stop` that reaches the main lane (and `forgetBot`) drops what was set aside.
- **Empty replies**: a native session-lane response with no text and no tool call would leave the session `running` with nothing working on it, so the host drops it and asks again once per turn (`EMPTY_SESSION_REPLY_NOTE`, never a chat message). Chat lanes end the turn.
- **Activity**: only the turn's last text stays in the chat; text before a tool becomes a `note` step. `describeToolCall` never returns raw arguments. File edits put only `EditedFile` summaries on `ActivityStep.files` (the card payload is rewritten on every step); patches go to `tool_call_diffs` (`ToolCallFinish.diffs`), fetched by the app per `toolCallId`. Claude Code's come from `tool_use_result.structuredPatch` (never keep its `originalFile`). Bash edits have no per-step diff.

## Providers and CLI engines

- **Providers** (`src/llm/`): a tool with `streamInput` (`DRAFT_TOOLS`) goes to Anthropic with `eager_input_streaming` (else the API buffers tool input) and its final input is re-read strictly from what streamed (`__invalidJson` when cut). `fitMemoryConfig` shrinks the memory budgets to the model's context window (`ResolvedModel.contextWindow` is already capped by the choice's `contextLimit`).
- **Effort** (rule in the root CLAUDE.md; `ModelLimits.efforts`, else the built-in catalog; null = unknown, sent as asked; [] = never sent):
  - Anthropic: `output_config.effort`, plus `thinking: {type: 'adaptive'}` only for `adaptiveThinking: 'opt_in'` models above `low`, so side one-shots stay without thinking.
  - OpenAI-compatible: the provider's `reasoningParam` (`auto` = `reasoning` on OpenRouter, `reasoning_effort` on api.openai.com or when the model has efforts registered, else nothing). OpenRouter `reasoning_details` go in `providerData` and are sent back. A plain `reasoning`/`reasoning_content` (vLLM, SGLang, llama.cpp) is sent back in the field it came in, only on the assistant messages after the last user message; without it Qwen-style models re-plan every step and loop. `reasoningReplay: off` stops it for a server that refuses the field.
- **Model per lane**: every turn calls `env.resolveModel(bot, {laneKey, model})` (`kind: 'native'` or `kind: 'cli'` + `engine` decides how the lane runs); model names the bot passes go through `env.resolveModelRequest`.
- **Engine contract** (`src/cli/`): each engine folder's `index.ts` exports a `CliEngineDriver` (`cli/engine.ts`) listed in `CLI_ENGINE_DRIVERS` (`cli/registry.ts`, the only file of `cli/` importing an engine folder). The driver holds everything engine-specific (native tools `nativeInMcp`, prompt wording, rotation, `profile`, `externalMcp`, `describeTool`, `mergeQuota`, `createSessions`…).
- The engine's `CliSessions` work out diffs, error codes (`CliErrorCode`), billing and `llm_calls` details inside the engine, so the host has one CLI turn engine (`host/turn/cli-turn.ts`) and `oneShot` one CLI path. Every engine runs the same cases against its fake in `cli/engine-contract.test.ts`.
- A CLI turn is one `llm_calls` row for many model requests. Each engine calls `io.onProgress` when a request completes (Claude Code: a new message id; Codex: `thread/tokenUsage/updated`; Antigravity: a finished `agent_response` with usage), priced like its result except Claude Code, whose real cost (`total_cost_usd`) only comes in `result`, so its progress is estimated from the public prices. `LiveCall` in `cli-turn.ts` records the row as `LLM_CALL_RUNNING` at the first one, rewrites it at most every `PROGRESS_INTERVAL_MS` (`env.updateLlmCall`) and the result replaces it under the same id (also `turn.llmCallId` from then on).
- Shared CLI pieces: `LaneSessions` (`lane-pool.ts`), `GuestProcess` (`guest-process.ts`: reconnecting event pump; joins `partial` stdout pieces with `LineAssembler`; `stopCliProcess` = EOF + SIGTERM, SIGKILL after `KILL_GRACE_MS`), `TurnInterrupt` (a stop while the process was starting counts too), `cliKeys` (stored keys: never rename).
- **Claude Code** (`src/claude-code/`): `claude -p` in stream-json as `agent` through `POST /procs`, one process per active lane, a fixed `--tools` list (never the native `Skill` tool), `--strict-mcp-config` with Milibot's MCP, `ENABLE_TOOL_SEARCH=false`, `COMPACT_SYSTEM_PROMPT` instead of the CLI prompt. Subscription mode uses the login done inside the VM (we never read credentials). Things that have broken before:
  - `claudeCodeProfile()` = hash of native tools + system prompt + prompt file + MCP tools (without memory). A different profile rotates the session silently; that's why prompt/tools/persona changes apply to existing sessions.
  - Rules + persona + memory bootstrap go in a 0600 file per lane (`--append-system-prompt-file`), never in argv: every VM user reads `/proc/*/cmdline`, and Linux caps one argument.
  - The CLI freezes the system prompt per session: the bootstrap is saved (`claude_code.bootstrap.<laneKey>`) and resent identically on `--resume`; new memory and the project block arrive in the input. No date in the prompt.
  - `total_cost_usd`/`modelUsage` in `result` are cumulative; `turnCost` (`sessions.ts`) subtracts the previous report of the same process. Several `result`s in one turn: only the last closes it; usage is summed.
  - Rotation (`cli/rotation.ts`, every engine): model changed, idle past `rotateIdleMinutes` (the CLI's cache lifetime) or context past `rotateContextTokens` (a lane's `contextLimit` wins).
  - Effort, output cap and context limit go as env (`claudeCodeTuningEnv`), never new flags: an older CLI ignores unknown env, and env is part of the process signature, so a change respawns with `--resume`.
  - `--resume` of a missing session returns `errors: ["No conversation found…"]` without `init`: retry in a new session.
  - Quota through `rate_limit_event` → `cli.usage.<providerId>`; plan through `claude auth status --json` (daemon `runtime/providers/cli-plan.ts`). A `rejected` `rate_limit_event` (or the limit wording) → `cli_usage_limit`; a process that cannot start is a failed turn (`cli_error`), never `turn_crashed`.
- **Codex** (`src/codex/`): `codex app-server` (JSON-RPC over stdio, no `jsonrpc` field) as `agent`, one process and one thread per lane (`codex.session.<laneKey>` = thread id), resumed with `thread/resume`. Pinned to `CODEX_VERSION`: `protocol.ts` is a subset of `codex app-server generate-ts` for that version and `fixtures/` are real recorded turns. Found against the real binary:
  - Everything goes in the thread's `config` (dotted keys): provider (`model_providers.milibot` with `env_key`, so an API key only lives in the process env), `mcp_servers.<slug>`, features. Milibot's server needs `omit_tools_from: ["code_mode"]` (else code-mode models never see MCP tools) and `default_tools_approval_mode: "approve"` (else `approvalPolicy: never` denies them).
  - Read-only helper lanes run with `sandbox: 'read-only'` (thread/start and thread/resume; part of the process signature). No output-token cap.
  - `features.multi_agent`/`goals`/`image_generation` and `skills.include_instructions` are off in lanes; `request_user_input` and `collaboration` stay offered, so the prompt points to `ask_user`/`subagent` and those server requests are refused (`answerServerRequest`). `ultra` effort is left out of `CODEX_MODELS`.
  - Mid-turn messages: `turn/steer` with `expectedTurnId` and `clientUserMessageId` (the `userMessage` item carrying that id means it was taken in). A steer after the turn ended fails: the rest goes in a follow-up `turn/start` in the same Milibot turn.
  - Usage: `thread/tokenUsage/updated` per model request (`last` summed per turn; cached tokens inside `inputTokens`). No cost reported: turns are priced from `CODEX_MODELS`.
  - Quota: `account/rateLimits/updated` is sparse (a null window keeps the last value, `mergeCodexRateLimits`), `resetsAt` in seconds. Errors mapped in `codexErrorCode`.
  - A missing thread (`no rollout found`) starts fresh with the memory recap. Native steps are `codex.*` in `tool_calls` (`CODEX_TOOLS`).
- **Antigravity** (`src/antigravity/`): `agy --agent <lane agent> --input-format stream-json --output-format stream-json -p=` as `agent`, one process per lane, resumed with `--conversation <id>` (`antigravity.session.<laneKey>`). Subscription only (`modelProvider` lives in agy's global settings, so an API key can't coexist with a login in one VM). Pinned to `ANTIGRAVITY_VERSION`; `fixtures/` are real recorded turns. Found against the real binary:
  - Milibot's rules, persona and the lane's MCP tool schemas are the lane's agent: `~/.milibot/agy-agents/<name>/agent.md` (the installer links `~/.gemini/config/agents` to it), whose body replaces agy's system prompt and whose `tools` list is validated (`command_status`/`send_command_input` are refused there). Under `--agent` the model gets MCP tool names but never their schemas (agy writes no schema files, and any other agy process, `/usage` included, empties them), hence `antigravityToolsPrompt`.
  - MCP config is one global file without env expansion: its `milibot` entry is Milibot's stdio bridge (daemon `agy-mcp-bridge.js`), which agy starts with the process env, so each lane's `MILIBOT_MCP_CONFIG` file (Milibot's server with the lane token + the bot's external servers) reaches it. Tools are called through `call_mcp_tool`; external ones are `<slug>__<tool>` (`antigravityMcpCall`). An agent's own `mcpServers` never start.
  - `--model <base>` without `--effort` is refused when the model has levels (`antigravityEffort` defaults to `high`). `init` arrives before stdin is read: a stored conversation agy lost shows as another `conversation_id` (warning on stderr) and the turn restarts fresh.
  - Each input gets its own `user_input` step and `result`, so mid-turn messages are counted, not echoed. `result.usage` is cumulative per conversation: usage is the sum of the turn's `agent_response` steps (input excludes cache reads, output includes thinking). Tool steps carry summarized parameters, never file contents: no per-step diffs. A long `run_command` goes to the background and agy wakes the model itself when it ends (a `system_message` step and more output before the `result`).
  - SIGINT ends the turn (`result` `interrupted`) and the process. A bare `RESOURCE_EXHAUSTED` (429) is server capacity agy already retried, not the plan's limit. No quota events: the daemon reads `agy -p /usage` (`ANTIGRAVITY_QUOTA_CHECK` after each turn).
  - Pictures: `generate_image` in a one-off agent with only that tool; agy reports no path, the files are `brain/<conversation>/<ImageName>_<ts>.<ext>` (read by the daemon).

## Tools (`src/tools/`)

- One file per family in `families/` (`defineTools`: `definitions`, `describe`, `labels`). `catalog.ts` spreads the families in the order models see the tools (part of every CLI session's profile and of the prompt cache), so a new tool goes at the end of its family. `policy.ts` holds what is offered where (`TOOL_FAMILIES`, `READ_ONLY_HELPER_TOOLS`, `LANE_TOOLS`, `toolsForLane`); `describe.ts` dispatches `describeToolCall`/`activityLine`. Argument helpers: `args.ts` (executing) and `families/kit.ts` (describing).
- Memory, messaging and `subagent` tools run in the host (`host/tools/host-tools.ts`, `HOST_TOOL_NAMES`); the rest in the daemon.
- `generate_image` is the `image_generation` setting family (no skill, so its guidance lives in the definition); image-output models are kept out of chat discovery (`IMAGE_ONLY_ID`).
- `web_search`/`web_fetch`: Claude Code keeps its own WebSearch/WebFetch (in its `nativeInMcp`), Antigravity its search_web/read_url_content; Codex keeps only its web search. `web_fetch` is in no family; `web_search` is a setting family. Side calls through `writeText` pass `turnId` so their cost shows under the turn; `writeText`/`oneShot` stream with `onText`.

## Prompts and skills text

- All model-facing text lives in `src/prompts/`, in English (system prompt, lane rules, turn notes `notes.ts`, host tool replies `tool-replies.ts`, summaries, triage, procedures, the skill catalog). Code elsewhere passes data in and never words a sentence the model reads. System prompt = `globalRules` (lean core) + persona (`# Your role` = the bot's whole `system_prompt`) + `# Team` + the user's language + the `# Skills` catalog (descriptions clipped at `CATALOG_DESCRIPTION_MAX`). Guidance for specific work lives in built-in skills.
- **When vs how**: deciding where work runs (`sizingRules`), whether to hand work to another bot and when to search the user's documents is in the core, since that decision is what makes a bot load the skill; skills only say how, and their descriptions name the actions to load them for, never the criterion. A "when to use" rule inside a skill body is never read in time. Taught procedures reach the catalog with `TAUGHT_CATALOG_PREFIX` for the same reason.
- One source per topic: `slides` and `documents-pdf` are the design skill's guides for decks and printed pages, so `design/guides/` has none for them; brief-writing for `design_draw` lives only in `guides/artwork.md`.
- Models call skill-gated tools without loading their skill, so a definition outweighs the skill: terse but never misleading. `session_start`'s goal is a brief that points to paths ("carry everything" made models read the whole project into it).
- The bot edits its persona with `update_own_prompt` (parsing and size check in the daemon's `runtime/bots/persona-edit.ts`; versions in `runtime/bots/prompt-versions.ts`). User-editable text stays in the user's language.
- Built-in skills (`skills/<slug>/SKILL.md`): parsed and rendered by `src/skills/format.ts`; description length checked by the daemon's `test/runtime/skills/library.test.ts`; bodies may use `{{bot_slug}}`, `{{#claude_code}}…{{/claude_code}}`/`{{^claude_code}}…` and `{{#cli}}…{{/cli}}`/`{{^cli}}…` (any CLI engine). Extra files (the design skill's `guides/*.md`) are listed by `skill_load`, read with `skill_read` and not templated. The drawing prompt (`prompts/design-draw.ts`) starts with `DRAW_PROMPT_MARKER`, which scripted runs route by.

## Memory and context (`src/memory/`)

- `buildContext` (`context-builder.ts`) builds from most to least stable, with cache breakpoints: system | workspace memory + knowledge catalog + project block | bot's pinned notes + summary chain | message tail | retrieved snippets and knowledge suggestions as the first block of the last user input. At most 4 breakpoints (Anthropic's limit).
- Async compaction per bot × conversation (`compaction.ts`): past `compactThresholdTokens` the old block is summarized (`summaries`, with levels); messages stay in the DB (`compacted = 1`). Model: `memory.summary_model` → the bot's model.
- Only the last `KEEP_SCREENSHOTS` screenshots stay as images; tool outputs past `MAX_TOOL_OUTPUT_CHARS` are cut in the middle. Token estimates: `estimateTokens` (`shared/src/core/text.ts`).
- `memory_save` refuses near-duplicates and notes past `MAX_NOTE_CHARS` (→ knowledge base). Eval: `pnpm --filter @milibot/agent eval:long-memory` (fake; real with `OPENROUTER_API_KEY`/`ANTHROPIC_API_KEY` + `EVAL_MODEL`).
